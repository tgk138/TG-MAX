# Telegram -> MAX Migration Service

> **Дизайн-документ:** [docs/plans/2026-02-22-tg-max-migration-design.md](docs/plans/2026-02-22-tg-max-migration-design.md)

---

# 1) Цель проекта

## 1.1. Бизнес-цель

Создать коммерческий SaaS-сервис "Telegram -> MAX Migration", который позволяет пользователю **перенести весь контент** из своего Telegram-канала (посты + медиа, включая альбомы) в выбранный канал/группу в MAX, используя:

* авторизацию в Telegram по номеру (код подтверждения + опционально 2FA),
* токен бота MAX для публикации.

**Монетизация:** 5 000 руб. за перенос канала + ручная активация. В будущем -- подписка на автоматический репост новых постов.

## 1.2. Продуктовая цель (что пользователь получает)

Пользователь заходит в веб-кабинет и за один сценарий:

1. подключает Telegram-аккаунт (номер -> код -> 2FA при необходимости),
2. выбирает канал-источник Telegram,
3. запускает импорт (с прогрессом и логом),
4. подключает MAX (вставляет токен бота),
5. получает список чатов/каналов MAX через `GET /chats` (где бот участник),
6. выбирает канал-назначение,
7. запускает публикацию (с прогрессом, ретраями, возобновлением после сбоев).

Пользователь **не обязан** сохранять даты. Нужно сохранить **порядок** постов.

## 1.3. Техническая цель

Построить надежную систему миграции с двумя независимыми процессами:

* **Telegram Ingest (Import)**: MTProto клиент на backend (Telethon) выгружает историю канала, группирует альбомы, скачивает медиа в Storage Layer, сохраняет нормализованные данные в Postgres.
* **MAX Publish**: Celery worker публикует нормализованные данные в MAX через Bot API (свой `MaxClient` на httpx: `uploads` -> `messages`), поддерживает альбомы (несколько вложений) и безопасно режет их на части при превышении лимитов.

Система должна быть:

* **идемпотентной** (idempotency key: `migration_id + order_index + unit_index`, не дублировать посты при повторном запуске),
* **резюмируемой** (resume после падения/рестарта, статусы в Postgres),
* **наблюдаемой** (прогресс-счётчики + таблица `job_events` для детального лога),
* **безопасной** (шифрование Telegram session и MAX token через единый `secrets.py`).

## 1.4. Ограничения и принципы (важно)

* Даты постов **не переносятся**, только порядок.
* Реакции/комменты/просмотры Telegram **не переносятся**.
* Альбомы Telegram (media_group) встречаются часто и должны поддерживаться как "логический пост".
* MVP тестируется локально в Docker на машине разработчика, затем разворачивается на VPS.
* Для MAX используем `GET /chats` для получения списка целей (не long polling).

# 2) Подробное ТЗ

## 2.1. Стек и инфраструктура

### Технологии (MVP)

* Backend: **Python 3.12 + FastAPI**
* Telegram: **Telethon**
* Очереди/джобы: **Celery**
* Broker: **Redis** (только как брокер, без хранения состояния)
* DB: **PostgreSQL** (единственный источник истины для состояния)
* UI: **Jinja2 + HTMX** (встроено в FastAPI, без отдельного фронтенда)
* Хранилище медиа: **Storage Layer** -- абстракция (`LocalStorage` на диск сейчас, `S3Storage` позже)
* MAX клиент: **свой `MaxClient`** на httpx (~8 методов), не сторонняя библиотека
* Reverse proxy: **Nginx** (или Caddy)
* Мониторинг: **Flower** (Celery dashboard) + structured logs

### Docker окружение

Собрать `docker-compose.yml` со службами:

* `nginx` (reverse proxy)
* `api` (FastAPI + Jinja2 UI)
* `worker` (Celery worker)
* `redis` (broker)
* `postgres`

Volumes:

* `./data/media` -> `/data/media` (для файлов)

## 2.2. Роли и права

* Пользователь сервиса: обычный пользователь SaaS.
* Telegram: пользователь авторизуется как **свой аккаунт** (MTProto).
* MAX: пользователь вводит токен бота; бот должен быть добавлен в цель (канал/группа) и иметь право публиковать.

## 2.3. Основные пользовательские сценарии

### S1: Подключить Telegram

1. UI: ввод телефона.
2. Backend: отправка кода через Telethon.
3. UI: ввод кода.
4. Backend: попытка логина.
5. Если включена 2FA -- UI показывает поле пароля; backend завершает логин.
6. Сессия сохраняется (шифрованно через `secrets.py`) и связывается с пользователем.

### S2: Выбор Telegram-канала

1. UI запрашивает список каналов/групп.
2. Пользователь выбирает канал-источник.
3. Создается "миграция" (draft) с выбранным каналом.

### S3: Импорт контента из Telegram

1. Пользователь нажимает "Импортировать".
2. API: проверяет status=draft, транзакционно ставит status=importing.
3. Enqueue Celery task `import_channel(migration_id)`.
4. Worker читает историю канала, формирует "логические посты", скачивает медиа в Storage Layer.
5. UI показывает прогресс и ошибки (HTMX polling).
6. По завершении статус миграции -> `imported`.

### S4: Подключить MAX (бот)

1. UI: пользователь вставляет токен бота.
2. Backend проверяет токен (`GET /me`) и сохраняет шифрованно.
3. UI: кнопка "Загрузить список чатов".
4. Backend вызывает `GET /chats` и сохраняет найденные чаты.
5. Пользователь выбирает цель (канал/группа) -> сохраняется в миграцию.

### S5: Публикация в MAX

1. Нажать "Опубликовать".
2. API: проверяет status=imported, транзакционно ставит status=publishing.
3. Enqueue Celery task `publish_to_max(migration_id)`.
4. Worker публикует посты в MAX **по порядку** с rate limit.
5. Альбомы публикуются как 1 сообщение, либо режутся на части.
6. По завершении статус миграции -> `done`.

## 2.4. Нефункциональные требования

### Надежность

* Любая операция должна быть **resume-friendly**.
* Публикация не должна создавать дубликаты: idempotency key `(migration_id, order_index, unit_index)` с уникальным индексом в БД.
* Dead-letter подход для failed задач с ручным retry из UI.

### Производительность

* Для MVP достаточно последовательной публикации 1-3 сообщения/сек на миграцию.
* Worker concurrency=1 на миграцию (ограничение для безопасности).
* Rate limits на Telegram (Telethon) и MAX (httpx) для защиты от бана.

### Безопасность

* Telegram session и MAX token хранить **только шифрованно** через единый `secrets.py`.
* Не логировать: коды, пароли 2FA, токены.
* Удаление данных: endpoint "Delete my data" (миграции + медиа файлы + сессии).

### Observability

* Прогресс (счетчики) в сущности миграции.
* Таблица `job_events` для детального лога ошибок и прогресса по шагам.
* Flower dashboard для мониторинга Celery.
* Structured logs (JSON).

* `id` uuid pk

* `type` text nullable (channel/group)

### Таблица `migrations`

* `id` uuid pk
* `user_id` fk
* `tg_connection_id` fk
* `tg_channel_peer` text (peer id / entity ref)
* `tg_channel_title` text
* `max_connection_id` fk nullable
* `max_target_chat_id` bigint nullable
* `status` enum: `draft|importing|imported|publishing|done|failed`
* counters:
  * `total_posts` int default 0
  * `imported_posts` int default 0
  * `total_media` int default 0
  * `downloaded_media` int default 0
  * `published_units` int default 0

**State machine с транзакционными переходами:**
```
draft --[start_import]--> importing --[complete]--> imported
                              |                        |
                              +--[fail]--> failed       |
                                            ^     [start_publish]
                                            |          |
                                            +-------- publishing --[complete]--> done
```

### Таблица `tg_posts` (логический пост)

* `id` uuid pk
* `migration_id` fk
* `tg_message_id` bigint (для одиночных сообщений)
* `album_key` text nullable (tg:{channel}:{grouped_id})
* `order_index` int (строго возрастающий)
* `text` text nullable
* `has_media` bool
* уникальность: (`migration_id`, `tg_message_id`) и/или (`migration_id`, `album_key`)

### Таблица `tg_media`

* `id` uuid pk
* `tg_post_id` fk
* `album_index` int default 0
* `media_type` enum: `photo|video|document|audio|voice|other`
* `file_path` text (путь в Storage Layer)
* `file_size` bigint
* `mime_type` text nullable
* `sha256` text nullable (для дедупа)

### Таблица `publish_units`

* `id` uuid pk
* `tg_post_id` fk
* `unit_index` int (0..k-1)
* `attachments_from` int
* `attachments_to` int
* `status` enum: `pending|uploading|sending|sent|failed`
* `max_message_id` text nullable
* `error_code` text nullable
* `error_text` text nullable
* `retry_count` int default 0
* уникальность: (`tg_post_id`, `unit_index`) -- idempotency key

### Таблица `job_events` (лог событий)

* `id` uuid pk
* `migration_id` fk
* `event_type` enum: `info|warning|error|progress`
* `phase` enum: `import|publish`
* `message` text
* `details` jsonb nullable
* `created_at`

## 2.6. Универсальная логика "альбомов"

### Импорт (Telethon)

* Если у сообщения есть `grouped_id` -> это элемент альбома.
* Все сообщения с одинаковым `(channel_id, grouped_id)` объединяются в один `tg_post`:
  * `album_key = f"tg:{channel_id}:{grouped_id}"`
  * `text` берём из первого сообщения альбома, где `message.text` не пустой.
* Медиа-элементы сохраняются в `tg_media` с `album_index` по порядку появления.

### Публикация (MAX)

* `MAX_ATTACHMENTS_PER_MESSAGE` (конфиг) по умолчанию 10.
* Если `len(media) <= MAX_ATTACHMENTS_PER_MESSAGE`:
  * 1 publish_unit: attachments 0..n-1 + текст
* Если больше:
  * создаём несколько publish_unit:
    * unit0: 0..9 + текст
    * unit1: 10..19 (без текста)
    * unit2: 20..n-1
* Порядок отправки строго по `order_index`, затем по `unit_index`.

## 2.8. Backend API (FastAPI) -- список эндпоинтов

### Telegram

1. `POST /api/tg/send_code`
   * input: `{ phone: string }`
   * output: `{ ok: true, needs_code: true }`

2. `POST /api/tg/confirm_code`
   * input: `{ phone: string, code: string }`
   * output: `{ ok: true, authed: true }` или `{ ok: true, needs_password: true }`

3. `POST /api/tg/confirm_password`
   * input: `{ phone: string, password: string }`
   * output: `{ ok: true, authed: true }`

4. `GET /api/tg/channels`
   * output: `[{ peer_id, title, username?, is_admin? }]`

### MAX

5. `POST /api/max/connect`
   * input: `{ bot_token: string }`
   * проверяет токен через `GET /me`, сохраняет шифрованно
   * output: `{ ok: true, bot_name: string }`

6. `POST /api/max/sync_targets`
   * вызывает `GET /chats` через MaxClient
   * output: `{ ok: true, found: number }`

7. `GET /api/max/targets`
   * output: `[{ chat_id, title, type? }]`

### Migrations

8. `POST /api/migrations`
   * input: `{ tg_peer_id, tg_title }`
   * output: `{ migration_id }`

9. `PATCH /api/migrations/{id}/set_target`
   * input: `{ max_chat_id }`
   * output: `{ ok: true }`

10. `POST /api/migrations/{id}/start_import`
    * транзакционный переход draft -> importing
    * output: `{ ok: true, job_id }`

11. `POST /api/migrations/{id}/start_publish`
    * транзакционный переход imported -> publishing
    * output: `{ ok: true, job_id }`

12. `GET /api/migrations/{id}`
    * output: статус + counters + последние job_events

13. `POST /api/migrations/{id}/retry_failed`
    * сбрасывает failed publish_units в pending, перезапускает
    * output: `{ ok: true, retried: number }`

14. `DELETE /api/migrations/{id}`
    * удаляет миграцию, медиа и все связанные данные

15. `DELETE /api/account/purge`
    * удаляет всё пользователя (GDPR-style)

## 2.9. Реализация MAX клиента (MaxClient на httpx)

Свой `MaxClient` на httpx с async поддержкой:

**Базовый URL:** `https://platform-api.max.ru`
**Авторизация:** заголовок `Authorization: <token>`
**Документация:** [dev.max.ru/docs-api](https://dev.max.ru/docs-api)

### Методы

| Метод | HTTP | Эндпоинт | Назначение |
|-------|------|----------|------------|
| `get_me()` | GET | `/me` | Проверка токена |
| `get_chats()` | GET | `/chats` | Список чатов бота (с пагинацией) |
| `get_chat(chat_id)` | GET | `/chats/{chatId}` | Детали чата |
| `get_membership(chat_id)` | GET | `/chats/{chatId}/members/me` | Проверка прав бота |
| `request_upload(type)` | POST | `/uploads` | Получить URL для загрузки |
| `upload_file(url, path)` | POST | `<upload_url>` | Загрузить файл по URL |
| `send_message(chat_id, text, attachments, format)` | POST | `/messages` | Отправить сообщение |
| `get_message(message_id)` | GET | `/messages/{messageId}` | Проверить отправку |

### Загрузка файлов (двухшаговый процесс)

1. `POST /uploads?type=image|video|audio|file` -> `{url, token}`
2. Загрузить файл по `url` (multipart, макс 4 ГБ)
3. Для video/audio: использовать `token` как attachment
4. Ошибка `attachment.not.ready` -- retry с backoff (0.5s, 1s, 2s, 4s, до SEND_RETRY)

### Типы файлов

* `image`: JPG, JPEG, PNG, GIF, TIFF, BMP, HEIC
* `video`: MP4, MOV, MKV, WEBM
* `audio`: MP3, WAV, M4A и другие
* `file`: любые типы файлов

## 2.10. Реализация Telegram импортера (Telethon)

Сделать `TelegramService`:

* `send_code(phone)` -- через Telethon send_code_request
* `sign_in_code(phone, code)` -- через Telethon sign_in
* `sign_in_password(phone, password)` -- через Telethon sign_in с password
* `list_channels()` -- iter_dialogs, фильтр по каналам/группам
* `export_channel(migration_id, peer_id)` -- основная логика импорта

Использовать `Telethon` логин-флоу: [docs.telethon.dev](https://docs.telethon.dev/en/stable/basic/signing-in.html)

Экспорт:

* чтение сообщений батчами (iter_messages, batch=TG_IMPORT_BATCH_SIZE)
* группировка по `grouped_id`
* скачивание медиа: `download_media(message, file=...)` -> Storage Layer
* задержка между батчами (TG_IMPORT_DELAY_MS) для защиты от rate limit
* обновление счётчиков в Postgres каждые N постов

## 2.11. Storage Layer

Абстракция для хранения медиа:

```python
class StorageBackend(ABC):
    async def save(self, key: str, data: bytes) -> str: ...
    async def read(self, key: str) -> bytes: ...
    async def delete(self, key: str) -> None: ...
    async def exists(self, key: str) -> bool: ...

class LocalStorage(StorageBackend):
    """Хранение на диске. MEDIA_ROOT из env."""

class S3Storage(StorageBackend):
    """Будущая реализация для S3/R2."""
```

## 2.12. Шифрование секретов (secrets.py)

Единый сервис для шифрования/дешифрования:

* Использует `SECRET_KEY` из env
* Алгоритм: Fernet (из cryptography) или AES-256-GCM
* Методы: `encrypt(plaintext) -> ciphertext`, `decrypt(ciphertext) -> plaintext`
* Применяется к: Telegram session string, MAX bot token

## 2.14. Критерии приёмки (Definition of Done)

1. Пользователь может подключить Telegram по номеру/коду (+ 2FA при необходимости).
2. Список Telegram-каналов отображается, можно выбрать канал.
3. Импортирует минимум 500 постов, включая альбомы, скачивает медиа в Storage Layer.
4. Пользователь подключает MAX токен (проверка через GET /me), загружает список чатов, выбирает чат/канал.
5. Публикация в MAX идёт в правильном порядке.
6. Альбомы:
   * публикуются как одно сообщение с несколькими вложениями,
   * либо автоматически режутся на части при превышении лимита вложений,
   * порядок внутри альбома сохраняется.
7. При рестарте контейнеров процесс можно возобновить без дублей (idempotency key).
8. Есть удаление миграции и очистка медиа.
9. Есть retry failed задач из UI.
10. Секреты зашифрованы, не логируются.
11. Все 5 Docker-контейнеров запускаются через docker-compose.
